## User requirements

- As a user, I want an AI report about my recent eating patterns, trends, and practical suggestions based on my goals, so that I can understand how my food choices relate to my targets.
- As a user, I want to edit the report prompt and add my OpenAI API key in Developer settings, so that I can tailor reports and use my own API account during development.
- As a developer, I want to launch weekly report generation on demand from the Developer menu, so that I can exercise the report flow without waiting for the scheduled Sunday run.
- As a user, I want the latest weekly report saved on this device and shown on a dedicated screen, so that I can reopen it quickly without another API request.
- As a user, I want to regenerate the report on demand even when a report for the same week is cached, so that it reflects updated diary data or prompt preferences.
- As a user, I want to choose Apple's on-device Foundation Model in report settings, so that I can generate reports without sending the weekly summary to OpenAI.
- As a user, I want reports generated automatically on Sunday mornings and a notification when one is ready, so that I can review them without remembering to start generation.
- As a user, I want the report to compare my intake with any goals I have for calories, alcohol, processed meat, and fiber, so that I can see what is on track and get relevant ideas for changes.
- As a user, I want practical, low-effort calorie-cut ideas when my logged intake is above my calorie goal, and a congratulations when I have logged consistently, so that advice reflects my week and recognizes the effort I made.
- As a user, I want no report generated, sent, or announced when I have not logged enough substantive food for a useful weekly review, so that I do not receive empty or misleading feedback.
- As a user, I want the production feature to be paid, so that access can be tied to a paid entitlement.

Implementation clarification: “weekly” means the previous seven completed local calendar days; only the latest report is retained. Compare that primary week with the two preceding completed local weeks. Include logged-day calorie, protein, and known-fiber averages, explicit cheat-day and gap-day counts, and each marked cheat day's calorie and percentage overage when a saved goal is available. Highlight single foods by calories, fiber, and protein using only the recent three-week window. Round fiber quantities to at most two decimal places, without trailing zeros in the UI. Do not infer gap days from empty unmarked dates or treat missing nutrient values as zero. Use the existing focus toggles as the user's opt-in to established app guidance. Do not ask for separate weekly targets. When enabled, use the same guidance shown in Trends: alcohol up to 2 drinks per day, processed meat at 0 servings per week, and fiber at 14 g per 1,000 calories based on the saved daily calorie goal (or 2,000 calories when absent). When a focus toggle is off, omit that guidance from the report request and suppress adherence suggestions for that topic. Treat a substantive week as food or meal entries on at least three distinct days; if it does not qualify, skip the model request and notification. Report generation must clearly disclose the diary summary and any food names sent to OpenAI. iOS background refresh is opportunistic and cannot guarantee a Sunday-morning run; a guaranteed schedule would require server-side scheduling and delivery.

## Architecture and data model

Add a report service alongside `OpenAIMealAnalysisClient` that builds a bounded weekly summary from `DiaryRepository` using a date-range snapshot. Include daily calorie and available macro totals, the saved calorie goal, established alcohol, processed-meat, and fiber guidance only for enabled focus toggles, and the minimum food-frequency details needed for trends and grounded suggestions. Do not add separate weekly target controls. Do not send HealthKit data or the full diary. Present the exact categories of information sent and require opt-in before the first automatic or manual report request.

Keep the editable prompt and automatic-generation preference in `UserDefaults`, the developer API key in the existing device Keychain credential store, and the single latest validated report in a small private Application Support JSON file. Write reports atomically and protect the file until first device unlock. This bounded report cache does not require changing `Diary.sqlite` or its schema; report generation is read-only against diary data. Store report window, generation date, prompt/model version, and rendered report content so the dedicated screen can show freshness and handle an older or corrupt cache visibly.

Before any model request, apply the substantive-logging gate. If fewer than three distinct days contain a food or meal entry in the report window, do not call OpenAI, replace the latest report, or schedule a ready notification; show an in-app explanation and keep any prior report clearly labeled with its own date range. For eligible weeks, use an iOS background refresh task for Sunday-morning generation and a local notification after successful generation, with notification permission requested in context and a generic lock-screen message. Add a deep link to the report screen. This can provide best-effort on-device automation only. Keep developer BYOK access separate from production access: a client-held key cannot securely support a paid distributed feature, so production requires a backend that owns provider credentials plus an explicit StoreKit entitlement or equivalent purchase decision.

Put model choice behind a versioned `ReportModelPolicy` that also sets reasoning effort and input/output limits. Default the report policy to `gpt-6-luna` with reasoning effort `none` and bounded tokens. Store the effective model and policy version with each report. Do not infer a model from its name or silently switch to another model when a request fails. For production, make the server the source of the active allowlisted model policy so a reviewed model change can roll out without an app release; keep the developer BYOK default in one app-level configuration. Promote a future low-cost model only after checking current model availability/pricing and running report quality, schema, and cost evaluations; otherwise retain the last validated model.

## Basic test cases

- Given diary history covering three completed weeks and a calorie goal, generating a report sends a bounded summary of those weeks, compares latest/previous/older trends, uses the saved prompt, and renders a validated report tied to the latest week and that goal.
- Given fractional fiber values, serialized daily and aggregate amounts round to at most two decimal places, and the screen omits unnecessary trailing zeros.
- Given explicitly marked cheat and gap days, the report counts them by week and distinguishes modest from substantial cheat-day calorie overages using the saved goal; empty unmarked dates are not treated as gaps.
- Given recent individual food entries and meal components, the report highlights calorie, fiber, and protein sources from the bounded three-week window without presenting unlogged foods as observed intake.
- Given alcohol, processed-meat, or fiber focus tracking enabled, the report uses the corresponding established app guidance and gives specific, practical next steps. When a toggle is off, the request omits its guidance and the report omits goal-adherence language for that topic. No separate weekly targets are requested.
- Given intake above the calorie goal, the report suggests easy changes grounded in repeatedly logged, calorie-bearing items. At or below goal it does not suggest cutting calories. Suggestions are optional and nonjudgmental.
- Given food or meal entries on fewer than three distinct days, generation makes no model request, saves no new report, and sends no notification. With an eligible week, the closing congratulations reflects the actual number of logged days and is omitted when logging was sparse.
- Given no goal, sparse logging, missing optional nutrients, or an empty week, the request labels missing data instead of inventing values; the report screen explains limited coverage.
- Given a successful response, the latest report survives app relaunch and is shown without a second API call. A subsequent successful report replaces it; a failed request leaves the previous report available.
- Given an eligible week with a same-week cached report, automatic generation reuses the cache; manual regeneration bypasses the cache, replaces it only after success, and keeps the previous report available on failure.
- Given the on-device model is selected, generation uses Apple's Foundation Models framework without loading or sending an OpenAI key, and settings explain that the summary and prompt stay on device. If the local model is unavailable, show that state without silently switching to OpenAI.
- Given a missing/invalid key, network failure, rate limit, oversized or malformed model response, generation shows a recoverable error and does not replace the saved report or send a ready notification.
- Given an edited prompt, the next report uses the saved version; removing the key or clearing the prompt behaves predictably and never writes the key outside Keychain.
- Given the default policy, a request uses `gpt-6-luna`, no reasoning effort, bounded input/output, and records the effective model/policy version. A future policy update changes the model only after validation; an unavailable model does not trigger an unapproved higher-cost fallback.
- Given a developer taps “Generate Weekly Report Now” in Settings → Developer → Developer Diagnostics, the same coordinator runs immediately, shows progress and a clear result/error, and displays the saved report; it still honors the substantive-logging gate and does not create a duplicate scheduled notification.
- Given notification permission is denied, report generation and in-app viewing still work. With permission granted, a notification is delivered only after a report is saved and opens the report screen.
- Given the background task runs late, is interrupted, or runs twice for the same week, it retries safely, avoids duplicate notifications/charges, and does not claim a guaranteed Sunday delivery.
- Given a production account without the paid entitlement, report generation is unavailable; an entitled account can use the server-backed path without exposing a provider key in the app.

## High-level implementation details

1. Add weekly summary and report value types, a versioned `ReportModelPolicy`, and an injectable report client/service beside `CalorieTracker/Data/OpenAIMealAnalysis.swift`. Default the policy to `gpt-6-luna` with reasoning effort `none`; apply strict input/output caps and record the effective model/policy version. Reuse the existing Responses API and Keychain patterns, with cancellation, HTTP error mapping, and response validation. Frame user prompt text as untrusted instructions and require non-medical, evidence-limited suggestions.
2. Add a repository-level date-range read for the previous seven completed local days and derive a compact summary with existing `DiaryEngine` totals. Reuse enabled focus toggles and the existing Trends guidance values; do not add separate report targets. Gate requests on food/meal entries on at least three distinct days. Handle daylight-saving boundaries and incomplete coverage explicitly; never mutate diary rows during generation.
3. Add a private latest-report file store and report-generation coordinator. Make writes atomic, preserve the prior report on failure, prevent overlapping requests, and track a stable local-week key to avoid duplicate generation and notifications.
4. Add a dedicated SwiftUI weekly report screen and navigation from the existing Trends/report area. Add report settings for prompt editing, OpenAI BYOK configuration/status, an on-device Apple Foundation Model toggle, automatic generation, and provider-specific privacy/billing copy. Manual generation from the report screen and Debug diagnostics bypass the same-week cache; automatic generation reuses a current-week report. Keep any existing OpenAI connection UI reusable rather than duplicating credential handling.
5. Register and reschedule a `BGAppRefreshTask` from the app lifecycle for the next Sunday morning in the device calendar, including expiration handling and foreground catch-up. Request local notification authorization in context, notify only after persistence succeeds, and route notification taps to the report screen. Document the system’s best-effort timing limit.
6. Update `docs/architecture.md`, `docs/setup-install.md`, and relevant privacy/setup documentation. Before production release, decide the backend API, StoreKit entitlement, pricing, subscription state handling, and account/data retention contract; do not ship the developer BYOK path as the paid production security boundary. Keep the production model allowlist and active policy server-side, and require an evaluation/review before promoting a newly named low-cost model.
7. Verify with injected clients, credential stores, clocks/calendars, notification and background-task adapters, and temporary report storage: summary boundaries, prompt use, goal/no-goal behavior, actionable suggestions, logging gate suppression, conditional congratulations, atomic replacement, failures, duplicate prevention, notification permission, and deep-link routing. Run the repository’s simulator checks and attempt the required `make phone-deploy`; report simulator, device, signing, or background-scheduling limits separately.

### Illustrative report

Example only; values and food names are fictional. The dedicated screen could present a compact summary followed by patterns, suggestions, and coverage:

> **Weekly eating report · Oct 12–18**  
> **Your logging:** You logged food on 6 of 7 days.  
> **Calories:** You averaged 2,150 calories on logged days, compared with your 2,000-calorie daily goal. If trimming calories is something you want to do, one easy option is swapping the 180-calorie sweetened coffee logged on five days for a 90-calorie version on some days. Each swap would save about 90 calories.  
> **Alcohol:** App guidance is up to 2 drinks per day; you logged 3 drinks on one day. If useful, you could choose another alcohol-free evening next week.
> **Processed meat:** App guidance is 0 servings per week; you logged 1. If useful, you could choose an unprocessed alternative next time.
> **Fiber:** Based on your 2,000-calorie goal, app guidance is 28 g per day; you averaged 21 g on logged days. You could try adding a fiber-containing food you enjoy, such as beans, fruit, or whole grains, on lower-fiber days.
> **Coverage:** 6 of 7 days logged. One day has no entries and is not counted as zero intake. Suggestions are optional, based on recorded diary data, and not a medical assessment.  
> **Congratulations on sticking with your logging this week.**

Include alcohol, processed-meat, or fiber guidance only when its matching focus toggle is enabled. Present enabled values as the app's guidance, never as a separately chosen user target.
