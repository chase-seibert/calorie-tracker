## User requirements

- As a user, I want an AI report about my recent eating patterns, trends, and practical suggestions based on my goals, so that I can understand how my food choices relate to my targets.
- As a user, I want to edit the report prompt and add my OpenAI API key in Developer settings, so that I can tailor reports and use my own API account during development.
- As a user, I want the latest weekly report saved on this device and shown on a dedicated screen, so that I can reopen it quickly without another API request.
- As a user, I want reports generated automatically on Sunday mornings and a notification when one is ready, so that I can review them without remembering to start generation.
- As a user, I want the report to compare my intake with any goals I have for calories, alcohol, processed meat, and fiber, so that I can see what is on track and get relevant ideas for changes.
- As a user, I want practical, low-effort calorie-cut ideas when my logged intake is above my calorie goal, and a congratulations when I have logged consistently, so that advice reflects my week and recognizes the effort I made.
- As a user, I want no report generated, sent, or announced when I have not logged enough substantive food for a useful weekly review, so that I do not receive empty or misleading feedback.
- As a user, I want the production feature to be paid, so that access can be tied to a paid entitlement.

Assumptions to confirm during implementation: “weekly” means the previous seven completed local calendar days; only the latest report is retained; the existing daily calorie goal is the only persisted nutrition target today, and current alcohol/fiber/processed-meat focus toggles are not targets. Add explicit optional report targets for alcohol, processed meat, and fiber, or show those only as neutral trends when no target is set. Treat a substantive week as food or meal entries on at least three distinct days (proposed threshold); if it does not qualify, skip the model request and notification. Report generation must clearly disclose the diary summary and any food names sent to OpenAI. iOS background refresh is opportunistic and cannot guarantee a Sunday-morning run; a guaranteed schedule would require server-side scheduling and delivery.

## Architecture and data model

Add a report service alongside `OpenAIMealAnalysisClient` that builds a bounded weekly summary from `DiaryRepository` using a date-range snapshot. Include daily calorie and available macro totals, the saved calorie goal, optional user-set alcohol, processed-meat, and fiber targets, and the minimum food-frequency details needed for trends and grounded suggestions. Add bounded local preferences for these optional report targets; do not treat existing focus toggles as targets. Do not send HealthKit data or the full diary. Present the exact categories of information sent and require opt-in before the first automatic or manual report request.

Keep the editable prompt and automatic-generation preference in `UserDefaults`, the developer API key in the existing device Keychain credential store, and the single latest validated report in a small private Application Support JSON file. Write reports atomically and protect the file until first device unlock. This bounded report cache does not require changing `Diary.sqlite` or its schema; report generation is read-only against diary data. Store report window, generation date, prompt/model version, and rendered report content so the dedicated screen can show freshness and handle an older or corrupt cache visibly.

Before any model request, apply the substantive-logging gate. If fewer than three distinct days contain a food or meal entry in the report window, do not call OpenAI, replace the latest report, or schedule a ready notification; show an in-app explanation and keep any prior report clearly labeled with its own date range. For eligible weeks, use an iOS background refresh task for Sunday-morning generation and a local notification after successful generation, with notification permission requested in context and a generic lock-screen message. Add a deep link to the report screen. This can provide best-effort on-device automation only. Keep developer BYOK access separate from production access: a client-held key cannot securely support a paid distributed feature, so production requires a backend that owns provider credentials plus an explicit StoreKit entitlement or equivalent purchase decision.

Put model choice behind a versioned `ReportModelPolicy` that also sets reasoning effort and input/output limits. Default the report policy to `gpt-6-luna` with reasoning effort `none` and bounded tokens. Store the effective model and policy version with each report. Do not infer a model from its name or silently switch to another model when a request fails. For production, make the server the source of the active allowlisted model policy so a reviewed model change can roll out without an app release; keep the developer BYOK default in one app-level configuration. Promote a future low-cost model only after checking current model availability/pricing and running report quality, schema, and cost evaluations; otherwise retain the last validated model.

## Basic test cases

- Given a diary with seven completed days and a calorie goal, generating a report sends only the selected weekly summary, uses the saved prompt, and renders a validated report tied to those dates and that goal.
- Given goals for alcohol, processed meat, and fiber, the report accurately compares logged amounts to each target and gives specific, practical next steps; without a target it shows a neutral trend or omits goal-adherence language. Focus toggles alone never count as goals.
- Given intake above the calorie goal, the report suggests easy changes grounded in repeatedly logged, calorie-bearing items. At or below goal it does not suggest cutting calories. Suggestions are optional and nonjudgmental.
- Given food or meal entries on fewer than three distinct days, generation makes no model request, saves no new report, and sends no notification. With an eligible week, the closing congratulations reflects the actual number of logged days and is omitted when logging was sparse.
- Given no goal, sparse logging, missing optional nutrients, or an empty week, the request labels missing data instead of inventing values; the report screen explains limited coverage.
- Given a successful response, the latest report survives app relaunch and is shown without a second API call. A subsequent successful report replaces it; a failed request leaves the previous report available.
- Given a missing/invalid key, network failure, rate limit, oversized or malformed model response, generation shows a recoverable error and does not replace the saved report or send a ready notification.
- Given an edited prompt, the next report uses the saved version; removing the key or clearing the prompt behaves predictably and never writes the key outside Keychain.
- Given the default policy, a request uses `gpt-6-luna`, no reasoning effort, bounded input/output, and records the effective model/policy version. A future policy update changes the model only after validation; an unavailable model does not trigger an unapproved higher-cost fallback.
- Given notification permission is denied, report generation and in-app viewing still work. With permission granted, a notification is delivered only after a report is saved and opens the report screen.
- Given the background task runs late, is interrupted, or runs twice for the same week, it retries safely, avoids duplicate notifications/charges, and does not claim a guaranteed Sunday delivery.
- Given a production account without the paid entitlement, report generation is unavailable; an entitled account can use the server-backed path without exposing a provider key in the app.

## High-level implementation details

1. Add weekly summary and report value types, a versioned `ReportModelPolicy`, and an injectable report client/service beside `CalorieTracker/Data/OpenAIMealAnalysis.swift`. Default the policy to `gpt-6-luna` with reasoning effort `none`; apply strict input/output caps and record the effective model/policy version. Reuse the existing Responses API and Keychain patterns, with cancellation, HTTP error mapping, and response validation. Frame user prompt text as untrusted instructions and require non-medical, evidence-limited suggestions.
2. Add a repository-level date-range read for the previous seven completed local days and derive a compact summary with existing `DiaryEngine` totals. Add explicit optional alcohol, processed-meat, and fiber report targets; do not reinterpret focus preferences as limits. Gate requests on food/meal entries on at least three distinct days, with the threshold documented for adjustment. Handle daylight-saving boundaries and incomplete coverage explicitly; never mutate diary rows during generation.
3. Add a private latest-report file store and report-generation coordinator. Make writes atomic, preserve the prior report on failure, prevent overlapping requests, and track a stable local-week key to avoid duplicate generation and notifications.
4. Add a dedicated SwiftUI weekly report screen and navigation from the existing Trends/report area. Add report settings for prompt editing, developer BYOK configuration/status, automatic generation, and clear privacy/billing copy. Keep any existing OpenAI connection UI reusable rather than duplicating credential handling.

Request local notification authorization in context, notify only after persistence succeeds, and route notification taps to the report screen. Document the system’s best-effort timing limit.

Keep the production model allowlist and active policy server-side, and require an evaluation/review before promoting a newly named low-cost model.
7. Verify with injected clients, credential stores, clocks/calendars, notification and background-task adapters, and temporary report storage: summary boundaries, prompt use, goal/no-goal behavior, actionable suggestions, logging gate suppression, conditional congratulations, atomic replacement, failures, duplicate prevention, notification permission, and deep-link routing. ### Illustrative report

Example only; values and food names are fictional. The dedicated screen could present a compact summary followed by patterns, suggestions, and coverage:

> **Weekly eating report · Oct 12–18**  
> **Your logging:** You logged food on 6 of 7 days.  
> **Calories:** You averaged 2,150 calories on logged days, compared with your 2,000-calorie daily goal. If trimming calories is something you want to do, one easy option is swapping the 180-calorie sweetened coffee logged on five days for a 90-calorie version on some days. Each swap would save about 90 calories.  
> **Alcohol:** Your goal was no more than 2 drinks this week; you logged 3. If you want to move closer to that target, you could choose one additional alcohol-free evening next week.  
> **Processed meat:** Your goal was no more than 2 servings; you logged 1, so you were within your target.  
> **Fiber:** Your goal was 25 g per day; you averaged 21 g on logged days. You could try adding a fiber-containing food you enjoy, such as beans, fruit, or whole grains, on lower-fiber days.  
> **Coverage:** 6 of 7 days logged. One day has no entries and is not counted as zero intake. Suggestions are optional, based on recorded diary data, and not a medical assessment.  
> **Congratulations on sticking with your logging this week.**

If no alcohol, processed-meat, or fiber target is set, that section should report only a neutral observed trend or be omitted; never imply the sample targets are defaults.
